# ADR-0029: Pinecone as the vector store for the knowledge (RAG) layer

Status: Accepted (owner, 2026-09-29; supersedes the OpenSearch k-NN choice in Intelligence README R11 and the index-tenancy design of I07 §3.4 / I00 §1.3) · Date: 2026-09-29 · Stage: I7 (I7a/I7b/I7c), I9, I10, I12, I13

## Context

The first Intelligence design put knowledge vectors in OpenSearch (one shared per-cell index, `_routing = tenant_id`, a mandatory tenant filter inside the k-NN query, hybrid BM25 + k-NN in one engine). The owner decided on 2026-09-29 to use **Pinecone** instead. OpenSearch stays for Stage 05d/10a telemetry search and is otherwise untouched. This ADR records how the design changes so the isolation, deletion and cost guarantees still hold.

Pinecone is a third-party managed service. Everything sent to it is data handed to a processor. The design therefore sends as little as possible and treats the index as a disposable projection of Postgres.

## Decision

1. **`VectorStore` port.** `knowledge-service` talks to vectors only through a small port: `upsert(namespace, records)`, `query(namespace, vector, top_k, filter)`, `delete_ids(namespace, ids)`, `delete_namespace(namespace)`, `namespace_exists/stats(namespace)`, `wait_visible(namespace, write_token)`. There is no method that takes a raw tenant id and no method that queries without a namespace. Adapters: **`pinecone` (production default)** and **`opensearch` (local and PR CI)**. The OpenSearch adapter reuses the previous design as a stand-in: the namespace becomes a routed keyword field and a mandatory filter inside the k-NN query, so the same contract applies. Pinecone Local is **not** the CI adapter because it does not support namespaces (verified above); it may be used only as an optional wire-compatibility smoke test whose namespace cases are skipped and not counted. A shared `VectorStoreContract` test suite runs against every adapter. PR CI runs it on the OpenSearch adapter (no paid account). A nightly and pre-release job runs it on a real Pinecone Starter index (free, us-east-1, synthetic fixtures only, key held as a repository secret that fork PRs cannot read). pgvector and Qdrant were considered as adapters and not built.
2. **What Pinecone stores.** Vectors and minimal metadata only: `chunk_id` (also the record ID), `doc_id`, `doc_version`, `tenant_ref` (the namespace pseudonym below), `trust` (T0-T3 tier), `acl_scope` (`min_role` today, site scopes reserved for Stage 09), `embedding_version`, `tombstone` (bool). **Never chunk text, titles, file names, site or bin IDs, user IDs or raw tenant IDs.** Chunk text stays in `greenguard_knowledge` under forced RLS and is fetched by `chunk_id` after retrieval; a hit whose chunk is missing, tombstoned, superseded or belongs to another tenant is dropped and counted. Only chunks that passed the I10 quarantine scan are ever upserted. Residual risk, stated plainly: embeddings can leak information about their source text (inversion attacks recover approximate text), so a Pinecone breach or operator access exposes semantic content even without text. Pinecone is a **data processor**: it goes on the subprocessor register, is covered by the DPA in the tenant-facing terms, and is excluded for tenants whose policy forbids it (decision 5).
3. **Tenant isolation.** One namespace per tenant, named `t_` + first 32 hex characters of `HMAC-SHA256(kb_ns_key, tenant_id)`; the raw tenant id never appears in Pinecone. `kb_ns_key` is one platform secret in Secrets Manager with a key id stored in the placement row; rotating it renames every namespace and is a full reindex (out of scope for v1). The namespace is **derived server-side from the authenticated principal inside the retrieval module**, from the token tenant only; no tool argument, prompt field or request body carries a tenant or namespace. A placement table `knowledge_index_placement(tenant_id, index_name, pinecone_project, region, ns_kid, status, created_at)` in `greenguard_knowledge` (forced RLS, tenant table) maps each tenant to its index; a tenant with no active row has no knowledge base. The **public corpus** is a separate index in a **separate Pinecone project** (curator key writes; runtime keys read-only), so a bug or leaked runtime key on the tenant path cannot write public content. Namespaces are the primary boundary; three checks back them up: (a) the query builder cannot construct a call without a namespace, (b) a post-retrieval assertion requires `hit.tenant_ref == namespace` and, after hydration, `chunk.tenant_id == principal.tenant`, and (c) metadata filters (`tombstone=false`, `acl_scope`, `embedding_version`) are applied in the query but **isolation never depends on them**, because it is unknown whether filters run before or after the ANN search. Capacity, honestly: a Standard index holds 100,000 namespaces and a project 20 indexes; Enterprise raises this to 1,000,000 per index and 200 per project. Only tenants that enable the knowledge base get a namespace, created lazily on first upload, so Tier 1 (10,000 organisations per cell) fits one index per cell and embedding version. **Tier U (10M organisations) is a modelled path, not a claim**: it needs on the order of 10 or more Enterprise-sized indexes per embedding version (before per-cell placement), higher limits by request, or BYOC, and it is unpriced. Tests: same query against two tenants' namespaces, namespace-name guessing (a forged `t_...` name from the client is impossible by construction and a direct Pinecone call with the runtime key for a foreign namespace is caught by the post-assertion in the adversarial fixture), and wrong-index routing (a placement row pointing at another tenant's index yields a request failure, not data).
4. **Hybrid retrieval: (b) Postgres full-text search fused with Pinecone dense results by RRF inside `knowledge-service`.** The lexical leg is a `tsvector` GIN index on `greenguard_knowledge.chunks` (tenant table, forced RLS) and on `public_chunks`; the dense leg is Pinecone. Rank lists are fused with RRF (k = 60), then the cross-encoder reranker, budgets, citations, HyDE and multi-query stay exactly as designed in I07 §3.5-3.6. Reasoning: (i) text never leaves Postgres, and the lexical leg is isolated by the RLS the platform already trusts; (ii) option (a), Pinecone sparse-dense, needs sparse vectors that are derived from the text (token-level leakage and another vector to keep consistent), and the newer Documents API with full-text fields needs the text inside Pinecone and is in public preview; (iii) option (c), keeping OpenSearch k-NN, is the decision that was reversed. Weakness accepted: Postgres text-search configurations cover English, Spanish, French and Portuguese but not Hindi or Punjabi (those use the `simple` configuration, so lexical recall is weaker and the multilingual dense leg carries them); GIN on tens of millions of chunks per cell is UNMEASURED and is an I13 item (the escape hatch is the OpenSearch adapter as lexical-only or a per-cell Postgres read replica).
5. **Data policy.** A tenant whose routing policy is `self_hosted_only` (README R21) or that is region-pinned (review O3) must not have content in managed Pinecone. In v1 **their knowledge base is disabled**: uploads return `knowledge_disabled_by_policy` (nothing is parsed, embedded or stored), retrieval returns `knowledge_disabled` with an honest message, no placement row can be created, no namespace exists, and sensor-fact tools still work. Enforced in four places: upload API, indexer, retrieval module and placement creation; a reconciliation job lists namespaces on each index, recomputes pseudonyms and must find zero namespaces for policy-blocked tenants. If a tenant flips to a blocking policy, the offboarding path in decision 6 runs. Lifting this needs an owner decision (README §8 Q21: BYOC, or the local adapter approved for that tenant class).
6. **Freshness and deletion.** Indexing: upsert in batches of at most 256 records (a 1,024-d vector is about 4 KB and the request cap is 2 MB / 1,000 records); keep the highest `x-pinecone-request-lsn`; poll a query on the same namespace until `x-pinecone-max-indexed-lsn` reaches it (bounded, then `indexing_delayed` and retry); **a document becomes `ready` only after it is visible**. Retrieval treats Pinecone as a hint and Postgres as truth (hydrate and drop), so a deleted document is never cited even while the index lags. Document deletion: tombstone + outbox event in one Postgres transaction (existing flow), indexer deletes the chunk IDs (from Postgres, so no filter sweep is needed), verifies with a fetch-by-ID and `describe_index_stats`, and stores a deletion-proof row. Tenant offboarding: `delete_namespace`, verify the namespace is absent and no record IDs fetch, then tombstone in Postgres. We create **no Pinecone backups or collections** for tenant indexes (an alarm fires if one appears in the project), so nothing on our side can restore deleted vectors. Whether Pinecone retains deleted data internally is unverified and is a contractual question (README §8 Q21) to close before I7c. Pinecone is added to the R26 deletion inventory (I00 §3.2): the tenant namespace, the public index (non-tenant), Pinecone-side retention (contractual), and any backup or collection (none allowed). The delete → restore → zero test (IT-05/TI-15) gains a Pinecone step: after restoring Postgres and replaying the deletion ledger, **rebuild the index from restored Postgres text and assert zero hits and no namespace for the deleted tenant**; restore replays the ledger before any index is rebuilt or served.
7. **Failure modes.** Every Pinecone call has a per-call timeout, bounded retries with jitter on 429/5xx inside the turn deadline, and a per-index circuit breaker. On outage, sustained 429 or breaker-open the retrieval module degrades to **lexical-only (Postgres FTS)** and sets `degraded_vector=true` in metadata and the trace; if the lexical leg is also down it returns 503 `knowledge_unavailable` and the advisor says knowledge search is unavailable and answers from tools only. It never presents an empty result as "no knowledge". Cost is metered per request (read units from the response if present, else the formula in the table) into `kb_vector_usage(tenant_id, day, read_units, write_units)` owned by knowledge-service, with a **per-tenant daily read-unit budget** (429 `kb_budget_exhausted` and lexical-only above it) and a platform monthly alarm at 50% and 90% of the Standard minimum plus usage. New K-cases K10 (rewritten), K32-K42 and gates are in I07 §3.7-3.8, TI-K11-TI-K17 in I07 §5, I09 (isolation, ACL, deletion gates) and I12 (metrics, SLO, chaos C6, DR).
8. **Cost.** Pinecone Standard is a **$50/month minimum** ($0.33/GB storage, ~$4/M write units, ~$16/M read units). Demo-scale usage (well under 1 GB, a few million write units at most, tens of thousands of cheap reads at 0.25 RU) is roughly $10 or less, so the bill is the $50 minimum. Four Secrets Manager entries for Pinecone keys are added ($0.40 each). `cost_model.json` is recomputed: infrastructure $544.52 (cap $600), total at caps $944.52, **headroom $55.48**, down from $107.08. The owner accepted a headroom target of at least $50 (was $100) as an explicit trade-off for choosing Pinecone; `scripts/check-intelligence-cost.mjs` reads the target from the JSON. The 24x7 certification month grows by the same $51.60 to $645.37, **over the $600 cap** (and over $1,000 in total if Claude is spent at both caps); a partial always-on soak of about 16.7 days ($580.49) fits. The choice for the 30-day G9 soak is owner question Q23 (I00 §5.1). Starter (free) and the OpenSearch adapter cover dev and CI. PrivateLink needs Enterprise ($500/month minimum), is **outside the $1,000 budget** and is an I13 production-hardening item.
9. **Operations, DR, security.** Metrics (no tenant labels): `vectorstore_request_seconds{op,stage}`, `vectorstore_errors_total{op,code}`, `vectorstore_read_units_total{stage}`, `vectorstore_write_units_total{stage}`, `vectorstore_circuit_state`, `vectorstore_freshness_wait_seconds`, `vectorstore_stale_hit_total`, `retrieval_degraded_total{mode}`. SLO and chaos case are in I12. **DR:** the index is a rebuildable projection; if it is lost, re-embed from Postgres chunk text under the platform indexing budget while retrieval runs lexical-only, and measure the rebuild in I13. **Secrets:** Pinecone API keys live in AWS Secrets Manager, are mounted only in `knowledge-service` pods, and never exist in the parser sandbox, agent pods, CI logs or developer laptops (developers use the OpenSearch adapter or Pinecone Local). **Network:** only `knowledge-service` may reach Pinecone; egress is restricted to the Pinecone data-plane and control-plane hostnames by NetworkPolicy (FQDN-capable policy or an egress proxy allow-list, chosen in I13); calls go over public TLS in the demo and PrivateLink in production. **Embeddings and reranking** stay behind `model-gateway` (I6); Pinecone integrated inference (embed/rerank endpoints) is **not used**, so every model call remains metered, traced and routed by tenant policy, and the index dimension is a property of the pinned embedding model version.

## Alternatives considered

| Option | Verdict |
|---|---|
| OpenSearch k-NN (previous design) | Kept only as the local/CI adapter. Rejected for production by the owner: another stateful cluster to size and secure (k-NN memory was an UNVERIFIED cost line) and a shared-index tenancy model that is harder to prove than a namespace. |
| pgvector in `greenguard_knowledge` | Would put vectors under RLS with no third party at all and is the simplest to delete from. Rejected as the production default because HNSW memory and vacuum behaviour on the shared cell database is a noisy-neighbour risk at Tier 1 and is unmeasured. Remains a credible fallback adapter if the Pinecone gate fails. |
| Qdrant (self-hosted or cloud) | Payload filtering and multi-tenancy are good, but it is one more stateful system or one more vendor with no advantage over Pinecone for this owner's decision. Not built. |
| Pinecone sparse-dense or Documents API for the lexical leg | Rejected in decision 4: sends text-derived data to the processor or needs the text there, and the Documents API is in public preview. |
