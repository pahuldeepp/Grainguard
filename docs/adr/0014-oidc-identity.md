# ADR-0014: OIDC identity with first-party membership mapping

Status: **Proposed — 2026-09-24**.

Owner: Stage 08 (BFF, Read API, dashboard). Stage 09 replaces the membership file
with a membership table and the production IdP decision (review R4).

## Context

The BFF and Read API already verify RS256 tokens through `@greenguard/tenant-auth`:
issuer, audience, `exp`/`nbf` with a clock tolerance, an RS256-only allow-list,
a JWKS cache with kid-miss refresh bounded by a cooldown, and `503 auth_unavailable`
when the key server cannot be reached. The tenant comes only from verified claims.
Review R4 notes that hosted IdPs cap organizations far below the 10M target, so the
IdP should prove identity only.

## Decision

1. **Local provider: Dex** (`ghcr.io/dexidp/dex:v2.43.1`, pinned by digest, 128 MB,
   read-only root) in the opt-in `infra/oidc/compose.yaml`. It implements
   authorization code + PKCE (S256), discovery and JWKS. Keycloak was not needed.
   Dex cannot add `tenant_id`/`roles` claims, which fits R4. Users are throwaway
   static fixtures. Their password is generated by `make bootstrap` into the ignored
   `.env` and bcrypt-hashed when the container starts. The dashboard is a public
   client with no secret.
2. **Claim mapping.** `createTokenVerifier` accepts an optional `mapIdentity`.
   When `AUTH_MEMBERSHIP_FILE` is set, the verified IdP payload is mapped via
   `${iss}|${sub}` to a GreenGuard membership `{tenantId, roles}`. Any `tenant_id` or
   `roles` the IdP asserts are overwritten. An identity without a membership gets
   `401 invalid_claims`. The token is still verified with all existing checks
   first. With no membership file, signed `tenant_id`/`roles` claims are used as
   before (the test-issuer path).
3. **Verifier configuration** is shared through `createTokenVerifierFromEnv`
   (`AUTH_ISSUER`, `AUTH_AUDIENCE`, `AUTH_JWKS_URL`, optional `AUTH_JWKS_CACHE_MS`,
   `AUTH_JWKS_COOLDOWN_MS`, `AUTH_CLOCK_TOLERANCE_SEC`, `AUTH_MEMBERSHIP_FILE`). The
   BFF forwards the same bearer and the Read API verifies it independently.
4. **Browser token storage: memory only.** `oidc-client-ts` keeps the user (access,
   ID and refresh tokens) in `InMemoryWebStorage`. Only the PKCE verifier, state and
   nonce use `sessionStorage` for the redirect round trip. Expiry renews through the
   refresh token (`signinSilent`), and a failed renewal signs out. A reload requires
   sign-in again. Dex has no `prompt=none` or session cookie, so iframe silent renew
   is not available. We chose this over Web Storage because an injected script
   cannot read tokens from storage. An httpOnly BFF session would remove the tokens
   from JavaScript entirely, but it needs a server-side session store and CSRF
   tokens. It is the preferred production follow-up and is not built here.
5. **CSRF.** Browser calls carry `Authorization: Bearer` and no ambient cookie, so a
   cross-site form cannot authenticate. Apollo's CSRF prevention stays on. If
   the httpOnly session is adopted, mutations need a double-submit or `SameSite=strict`
   plus an origin check.
6. **Logout.** Dex publishes no `end_session_endpoint`. Sign-out therefore always
   clears the query cache, UI selections and the in-memory user. It redirects to the
   IdP only when the provider advertises RP-initiated logout.

## Consequences

- JWKS outage behaviour is bounded. A cached key keeps verifying until
  `AUTH_JWKS_CACHE_MS` (default 10 min) after the last successful fetch, and every
  request after that returns 503. A kid miss inside the cooldown returns 401
  without calling the key server. After the cooldown it reloads once, and a failed
  reload returns 503.
- Dex memory storage rotates the signing key on restart. Old tokens then fail and
  new tokens verify after one refresh.
- The membership file is a dev fixture. Production membership, revocation and
  audit belong to Stage 09.
- The saga API rereads the local membership file for each request, so removing
  a member immediately denies saga operations. The BFF and Read API atomically refresh their
  maps every `AUTH_MEMBERSHIP_REFRESH_MS` (default 30 seconds; 0 disables).
  Failed reads or validation retain the last good map for at most
  `AUTH_MEMBERSHIP_MAX_STALE_MS` (default 5 minutes since the last successful load),
  then log an error and return `401 invalid_claims` for all membership lookups.
  Roles must be viewer, operator, admin or device. The refresh timer is unreferenced;
  verifier `close()` stops it. This is not immediate platform-wide revocation.
- Membership files reject duplicate identity keys and noncanonical tenant UUIDs.
