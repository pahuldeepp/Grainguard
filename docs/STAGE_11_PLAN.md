# Stage 11 — End-to-end observability, SLOs and runbooks

Stage 11 targets the operator question: **is the whole platform healthy, and if not, where and why?** The approved scope and exit criteria are in the [Stage 11 implementation plan](../../outputs/STAGE_11_IMPLEMENTATION_PLAN.md).

## Current verified state

The Stage 11 observability implementation is merged into `codex/greenguard-domain-product` from `codex/stage-11-observability` (merge commit recorded in Git). Stage 10d verification was previously run on the integrated working-tree contents using the isolated database harness; the shared development database was not used for that verification.

- The local profile defines OpenTelemetry Collector, Prometheus, Grafana, Loki, Tempo, Alertmanager, node exporter, and optional Postgres/AWS/streaming exporters. Prometheus loads platform, broker, and SLO rules. Five dashboards are provisioned: platform overview, service/dependency health, broker health, and two SLO views.
- Go and Nest HTTP RED instrumentation and PostgreSQL client-pool/query-duration signals are present. Go pgx pools expose acquisition saturation/wait. The TypeScript package provides bounded Prisma pool/query metrics. A cardinality audit rejects tenant, device, request, event, trace, and span identifiers as metric labels.
- Prometheus rule validation and synthetic tests pass for 23 platform, 39 broker, and 65 SLO rules. The runbook contract checker passes for all 55 alerts. AWS CloudWatch configuration now renders from validated explicit function/table allowlists.
- The isolated backend profile reached ready state. Grafana provisioned all five dashboards; Prometheus loaded all four alert groups. A live OTLP smoke produced a Prometheus metric and a Tempo trace. The Kafka exporter observed one broker; the Connect state exporter reported Connect and Schema Registry up and all returned connector states. These are local/dev checks, not production availability evidence.
- The OTel Collector exports OTLP logs to Loki's native OTLP endpoint. Telemetry-ingest emits bounded 5xx logs with active trace context and per-route/status burst suppression. A live `503 binding_feed_stale` log was retrieved from Loki and its trace/span IDs matched the corresponding Tempo server span. The accepted ingest request and CDC producer span also share the persisted trace context. This proves real trace/log drill-down for telemetry-ingest and causal propagation through CDC, not coverage across every service.
- The scaled failure rehearsal passes all 55 configured alert scenarios through pending/firing (or immediate firing for integrity invariants), a local webhook notification with the rule's severity and runbook, recovery, and resolved notification. This includes all Kafka/CDC, RabbitMQ, replication slot, binding feed, integrity, platform, and four SLO burn routes. These are synthetic metrics delivered to an isolated local sink.

## Still open

1. **Integrated verification:** the isolated full `make verify` passed on 2026-09-26 against that day's integrated tree; it does not validate all later domain-product edits currently present in the shared checkout. The live `control-outbox` stall was resolved in dev: Debezium heartbeat/action-query settings and its internal Kafka topic were applied, and source offset/confirmed flush LSN advanced on repeated samples. A Connect JMX exporter configuration defect has now been fixed in source (reachable Compose hostname and correct config mount), and isolated runtime checks observed Connect JMX plus confirmed-flush-LSN advancement. Re-run the full repository gate after the current unrelated domain work is integrated.
2. **Dependency exporters:** isolated runtime checks observed the Kafka and Connect targets, and the confirmed-flush-LSN gauge advanced for the inventory slot during sampling. PostgreSQL exporters can scrape an isolated PostgreSQL 16 instance with a least-privilege observer role. RabbitMQ exposes queue metrics on its Docker network, though the running dev container does not publish the scrape port to the host. PostgreSQL slow-query fingerprints/lock waits and provider outcome metrics are incomplete. AWS CloudWatch/Lambda checks remain unverified because this environment has no configured AWS CLI identity/account evidence; live cloud metrics and Lambda Insights require an authorized AWS environment.
3. **Service and journey coverage:** the isolated inventory outbox/CDC/Kafka/binding/freshness recovery journey passed its recorded assertions, including poison quarantine, restart/replay, heartbeat checkpoints, stale-feed rejection, and recovery. A telemetry ingest request was causally linked to the CDC producer span. This does not yet prove full service/container USE, provider delivery outcomes, risk/projection/notification freshness, or saturation under representative load.
4. **Trace/log drill-down:** live trace context propagates from telemetry-ingest HTTP through the CDC producer using the outbox traceparent. Separately, a live 503 freshness-gate request emitted an OTLP log retrieved from Loki; the log's trace/span identifiers matched its Tempo server span. This failure path is rejected before event creation, so it correctly has no CDC span. Risk/projection/notification trace coverage, database fingerprint spans, and fault localization across those services still need live evidence.
5. **SLOs and paging:** [SLO targets](SLOS.md) remain proposed and unapproved. Validate SLI denominators, thresholds, and recording cost against representative load; execute burn alerts through Alertmanager routing and obtain owner approval. No production contact point has been configured.
6. **Rehearsals and evidence:** synthetic alert rehearsals now cover the configured alert paths, with firing and resolved notifications delivered to isolated local webhook sinks. These prove rule evaluation and local notification flow only; production paging, live dependency fault injection, representative cardinality/load evidence, AWS signals, and approved SLOs remain outstanding. Stage 11 stays in progress until production-representative evidence and SLO owner approval are accepted.

The currently configured optional targets show down/unknown when their profile or app is not started. Do not treat synthetic series, unavailable dependencies, or proposed SLOs as live health or production commitments.
