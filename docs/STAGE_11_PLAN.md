# Stage 11 — End-to-end observability, SLOs and runbooks

Stage 11 targets the operator question: **is the whole platform healthy, and if not, where and why?** The approved scope and exit criteria are in the [Stage 11 implementation plan](../../outputs/STAGE_11_IMPLEMENTATION_PLAN.md).

## Current verified state

Work remains on the isolated, uncommitted branch `codex/stage-11-observability`, based on `176f449`; it has not yet been integrated with the accepted Stage 10d state.

- The local profile defines OpenTelemetry Collector, Prometheus, Grafana, Loki, Tempo, Alertmanager, node exporter, and optional Postgres/AWS/streaming exporters. Prometheus loads platform, broker, and SLO rules. Five dashboards are provisioned: platform overview, service/dependency health, broker health, and two SLO views.
- Go and Nest HTTP RED instrumentation and PostgreSQL client-pool/query-duration signals are present. Go pgx pools expose acquisition saturation/wait. The TypeScript package provides bounded Prisma pool/query metrics. A cardinality audit rejects tenant, device, request, event, trace, and span identifiers as metric labels.
- Prometheus rule validation and synthetic tests pass for 23 platform, 39 broker, and 65 SLO rules. The runbook contract checker passes for all 55 alerts. AWS CloudWatch configuration now renders from validated explicit function/table allowlists.
- The isolated backend profile reached ready state. Grafana provisioned all five dashboards; Prometheus loaded all four alert groups. A live OTLP smoke produced a Prometheus metric and a Tempo trace. The Kafka exporter observed one broker; the Connect state exporter reported Connect and Schema Registry up and all returned connector states. These are local/dev checks, not production availability evidence.
- The scaled failure rehearsal now passes 17 scenarios through pending/firing (or immediate firing for the integrity invariant), webhook notification, recovery, and resolved notification. It includes synthetic RabbitMQ backlog, PostgreSQL slot inactivity, and `IntegrityCDCQuarantined`; SLO burn and most broker alerts still have promtool coverage only, not equivalent sink rehearsals.

See [local-profile validation](../evidence/stage11/local-profile-validation.md), [broker validation](../evidence/STAGE_11_BROKER_VALIDATION.md), [SLO validation](../evidence/STAGE_11_SLO_VALIDATION.md), and [rehearsal validation](../evidence/STAGE_11_REHEARSAL_VALIDATION.md) for commands, versions, and limits.

## Still open

1. **Stage 10d integration:** rebase/merge this work onto the accepted Stage 10d commit, resolve instrumentation/Compose overlap, and rerun verification after integration. The isolated full `make verify` against current Stage 10d working-tree contents completed migrations, unit/type/lint checks, Go race tests, and production builds successfully. The existing jobs-worker expected-intent assertions were updated and passed in that run. A shared-database heartbeat validator and tests guard checked-in connector files. The live `control-outbox` stall is resolved in dev: 30-second Debezium heartbeat/action-query config and its internal Kafka topic were applied; source offset and confirmed flush LSN advanced on repeated samples, with retained WAL falling to 15,224 bytes. JMX remains unavailable in the running Connect container, but is no longer needed to establish slot progress.
2. **Dependency exporters:** Prometheus runtime checks confirmed Kafka and Connect targets can work. RabbitMQ's Prometheus plugin is enabled and returns queue metrics on its Docker network, but the running dev container does not publish the scrape port to the host. The slot exporter cannot authenticate because `greenguard_observer` is absent. PostgreSQL slow-query fingerprints/lock waits and provider outcome metrics are incomplete. Live AWS calls are unverified; credentials, permissions, cost, and Lambda Insights require the configured AWS account.
3. **Service and journey coverage:** most app targets were not running in the isolated profile. RED and client pool metrics do not yet prove full service/container USE, provider delivery outcomes, projection freshness, or saturation on a representative load. Run the critical request/outbox/CDC/Kafka/risk/projection/notification journey after Stage 10d integration.
4. **Trace/log drill-down:** the smoke proves OTLP reaches Tempo and OTLP metrics reach Prometheus. It does not prove causal context across the critical journey, database fingerprint spans, structured log export to Loki, trace-to-log pivots, retries, or fault localization.
5. **SLOs and paging:** [SLO targets](SLOS.md) remain proposed and unapproved. Validate SLI denominators, thresholds, and recording cost against representative load; execute burn alerts through Alertmanager routing and obtain owner approval. No production contact point has been configured.
6. **Rehearsals and evidence:** extend sink-based fault/recovery rehearsals to remaining broker and SLO burn rules, run the runbooks against real local dependencies, and capture target status, dashboard queries, trace/log proof, cardinality growth, alert routing, and recovery. Stage 11 stays in progress until these artifacts and Stage 10d integration are accepted.

The currently configured optional targets show down/unknown when their profile or app is not started. Do not treat synthetic series, unavailable dependencies, or proposed SLOs as live health or production commitments.
