# Stage 11 — End-to-end observability, SLOs and runbooks

Stage 11 targets the operator question: **is the whole platform healthy, and if not, where and why?** The approved scope and exit criteria are in the [Stage 11 implementation plan](../../outputs/STAGE_11_IMPLEMENTATION_PLAN.md).

## Current verified state

The Stage 11 observability implementation is merged into `codex/greenguard-domain-product` from `codex/stage-11-observability` (merge commit recorded in Git). Stage 10d verification was previously run on the integrated working-tree contents using the isolated database harness; the shared development database was not used for that verification.

- The local profile defines OpenTelemetry Collector, Prometheus, Grafana, Loki, Tempo, Alertmanager, node exporter, and optional Postgres/AWS/streaming exporters. Prometheus loads platform, broker, and SLO rules. Five dashboards are provisioned: platform overview, service/dependency health, broker health, and two SLO views.
- Go and Nest HTTP RED instrumentation and PostgreSQL client-pool/query-duration signals are present. Go pgx pools expose acquisition saturation/wait. The TypeScript package provides bounded Prisma pool/query metrics. A cardinality audit rejects tenant, device, request, event, trace, and span identifiers as metric labels.
- Prometheus rule validation and synthetic tests pass for 23 platform, 39 broker, and 65 SLO rules. The runbook contract checker passes for all 55 alerts. AWS CloudWatch configuration now renders from validated explicit function/table allowlists.
- The isolated backend profile reached ready state. Grafana provisioned all five dashboards; Prometheus loaded all four alert groups. A live OTLP smoke produced a Prometheus metric and a Tempo trace. The Kafka exporter observed one broker; the Connect state exporter reported Connect and Schema Registry up and all returned connector states. These are local/dev checks, not production availability evidence.
- The OTel Collector exports OTLP logs to Loki's native OTLP endpoint. A local synthetic trace and log with the same trace/span identifiers were accepted by Tempo and Loki, and Loki returned the log through its `trace_id` metadata filter. This proves the backend correlation path, not correlation across a real GreenGuard application journey.
- The scaled failure rehearsal passes all 55 configured alert scenarios through pending/firing (or immediate firing for integrity invariants), a local webhook notification with the rule's severity and runbook, recovery, and resolved notification. This includes all Kafka/CDC, RabbitMQ, replication slot, binding feed, integrity, platform, and four SLO burn routes. These are synthetic metrics delivered to an isolated local sink.

See [local-profile validation](../evidence/stage11/local-profile-validation.md), [broker validation](../evidence/STAGE_11_BROKER_VALIDATION.md), [SLO validation](../evidence/STAGE_11_SLO_VALIDATION.md), and [rehearsal validation](../evidence/STAGE_11_REHEARSAL_VALIDATION.md) for commands, versions, and limits.

The isolated live inventory/CDC/binding/freshness journey and its Tempo/Loki inspection are recorded in [live journey evidence](../evidence/STAGE_11_LIVE_JOURNEY.md). It passed its listed recovery assertions, but did not establish a single causally linked trace across the full application or application log correlation.

## Still open

1. **Integrated verification:** Stage 11 is merged with the current Stage 10d/domain-product work. The isolated full `make verify` passed on 2026-09-26 against the merged tree; focused Prometheus rule and observability validators also pass. A shared-database heartbeat validator and tests guard checked-in connector files. The live `control-outbox` stall is resolved in dev: 30-second Debezium heartbeat/action-query config and its internal Kafka topic were applied; source offset and confirmed flush LSN advanced on repeated samples, with retained WAL falling to 15,224 bytes. JMX remains unavailable in the running Connect container, but is no longer needed to establish slot progress.
2. **Dependency exporters:** Prometheus runtime checks confirmed Kafka and Connect targets can work. Both PostgreSQL exporters now scrape an isolated PostgreSQL 16 instance successfully (`pg_up=1`) using a least-privilege `greenguard_observer` role; this does not grant access to the shared dev database. RabbitMQ's Prometheus plugin returns queue metrics on its Docker network, but the running dev container does not publish the scrape port to the host. PostgreSQL slow-query fingerprints/lock waits and provider outcome metrics are incomplete. Live AWS calls are unverified; credentials, permissions, cost, and Lambda Insights require the configured AWS account.
3. **Service and journey coverage:** the isolated inventory outbox/CDC/Kafka/binding/freshness recovery journey now passes (see live journey evidence). Most app targets were not running together. RED and client pool metrics do not yet prove full service/container USE, provider delivery outcomes, risk/projection/notification freshness, or saturation on a representative load.
4. **Trace/log drill-down:** backend-level trace/log correlation is proven with a synthetic shared trace ID. Live inspection proved that a telemetry-ingest HTTP server span and CDC producer span share the persisted trace context. Loki returned no application log for that trace. Risk/projection/notification trace coverage, application logs, database fingerprint spans, and fault localization still need live app evidence.
5. **SLOs and paging:** [SLO targets](SLOS.md) remain proposed and unapproved. Validate SLI denominators, thresholds, and recording cost against representative load; execute burn alerts through Alertmanager routing and obtain owner approval. No production contact point has been configured.
6. **Rehearsals and evidence:** the synthetic sink harness now covers all 55 alert paths, with firing and resolved notifications verified. Live dependency faults, application journeys, production routing, representative cardinality/load evidence, and approved SLOs remain outstanding. Stage 11 stays in progress until production-representative evidence and approved SLOs are accepted.

The currently configured optional targets show down/unknown when their profile or app is not started. Do not treat synthetic series, unavailable dependencies, or proposed SLOs as live health or production commitments.
