# EventBridge alert bridge

The bridge consumes canonical alert lifecycle events from Kafka and emits the unchanged event to EventBridge for the lifecycle mirror. Critical `alert.opened`, `alert.escalated`, and `alert.resolved` transitions additionally receive the `alert.critical.serverless` marker. This routing is unconditional. Warning/non-critical notifications never receive the critical marker and remain on RabbitMQ. `jobs-worker` applies the same unconditional rule: it retains inbox evidence for critical transitions but creates no RabbitMQ notification intents.

Run unit tests with `make serverless-bridge-test`. EKS deployment needs Kafka access, `EVENT_BUS_NAME`, `BRIDGE_QUARANTINE_QUEUE_URL`, and the optional Terraform Pod Identity inputs for the exact EventBridge bus ARN and SQS quarantine queue ARN. Terraform binds the `greenguard/eventbridge-bridge` service account to permissions limited to `events:PutEvents` on that bus and `sqs:SendMessage` on that queue. The bridge uses the AWS SDK credential chain; no static AWS keys belong in the pod. Use approved Kafka security settings; never put credentials in command-line arguments or logs. EventBridge and SQS are at-least-once. The direct AWS delivery Lambda uses stable per-channel UUIDv5 IDs plus conditional DynamoDB claims and never falls back to RabbitMQ after an AWS failure.

The worker's loopback-only `/healthz` endpoint reports a fresh poll loop; `/readyz` becomes healthy only after Kafka assigns a subscribed partition. Kubernetes uses local exec probes, so these endpoints are not exposed through pod ingress. AWS SDK clients are constructed before readiness, but the bridge intentionally does not send synthetic events or queue messages as a health check. Readiness therefore does not prove live AWS credentials/IAM permissions; the disposable-environment acceptance smoke must send a real authorized lifecycle event and verify EventBridge plus quarantine behavior.
