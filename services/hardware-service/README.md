# Physical sensor hardware participant

This service owns the pre-registered sensor hardware registry in `greenguard_hardware`. It handles `asset.reserve`, `asset.configure`, and `asset.release` for Stage 07 provisioning. The device-service owns `inventory.activate`/`inventory.deactivate`; the telemetry owner decides `binding.await`. A hardware row is registered by inventory operations before provisioning; a missing asset is a definitive business rejection.

Commands arrive on `greenguard.saga.commands.v1` keyed by `tenant_id:saga_id`. The JSON envelope has `tenant_id`, `saga_id`, `command_id`, `step`, `saga_version`, `fencing_token`, and `payload` with the same tenant/saga plus `asset_id` and `device_id`. Results use `greenguard.saga.results.v1` with the same identity fields, a stable `result_id`, and `outcome` of `succeeded` or `rejected`.

Each command runs in a tenant-scoped transaction. An advisory lock serializes deliveries of its command ID; `SELECT ... FOR UPDATE` serializes asset claims and state changes. Reserve/release transactions record the physical registry change, an immutable receipt, and a result outbox row. Configure records a durable `pending` receipt and commits the Kafka source offset. A separate MQTT dispatcher republishes pending commands with the same command ID until the device responds. The device acknowledgement must match tenant, asset, device, saga, version, fencing token, and per-asset HMAC key before the registry changes to `configured` and a success result enters the Kafka outbox. A timeout leaves the result unknown/pending; it is never a business rejection. When the saga compensates by releasing the asset, the release transaction finalizes the outstanding configure receipt as `cancelled`; a late acknowledgement is then refused and replay returns no result. The dispatcher claims at most 100 receipts per pass in least-recently-dispatched order with `FOR UPDATE SKIP LOCKED` (migration `000003`), so blocked receipts move to the back and cannot starve newer configurations; a receipt whose asset is no longer reserved by its saga is cancelled on claim. If it crashes at any boundary, Kafka redelivery returns the original receipt/result ID. Database or transport failures are errors, never business rejections. An unknown stale fencing token stops the worker for operator inspection.

Register hardware using an authenticated inventory operation before starting the saga. The current slice has no registration API; the live test inserts a fixture directly. Registration must install a unique random `mqtt_ack_secret` of at least 32 bytes per sensor in the hardware database. The application role cannot enumerate tenant data. The dispatcher calls fixed, ID-only security-definer selectors, then reloads each command/result under a tenant-scoped RLS transaction. The local Compose overlay provides an anonymous Mosquitto broker solely for development. Production deployment requires TLS transport, broker client authentication, per-device publish/subscribe ACLs, key rotation, and a firmware implementation that persists command IDs and signs acknowledgements. The broker must not retain acknowledgement messages; the subscriber ignores duplicate acknowledgements after the receipt is finalized.

```bash
make hardware-migrate hardware-test

```

`HARDWARE_DATABASE_URL` uses the RLS-limited runtime role through PgBouncer; `HARDWARE_DIRECT_URL` runs live tests through the direct port; `HARDWARE_MIGRATION_URL` uses the schema owner. `KAFKA_BROKERS` and `MQTT_BROKER_URL` are required for `go run ./cmd/worker`. Optional `MQTT_USERNAME`/`MQTT_PASSWORD` authenticate the broker client. For a private TLS broker, set `MQTT_BROKER_URL=tls://mqtt.<namespace>.svc.cluster.local:8883` and `MQTT_CA_FILE` to a mounted PEM CA file. The worker checks the broker certificate against that hostname; malformed or missing CA files fail startup. Local `tcp://` remains available only without `MQTT_CA_FILE`. Production must enable persistent MQTT sessions and broker-side persistence for QoS 1 deliveries. Startup requires `MQTT_CLIENT_ID`, a stable identity per worker replica, so the session survives pod replacement. The worker acknowledges device messages only after the database transition commits. Database handling has a 10-second deadline; on failure, the worker reconnects with bounded connection retry so the broker can redeliver the uncommitted message. It serializes acknowledgement handling to bound concurrent database work and waits for subscription readiness before starting worker loops.

For the local Stage 07 end-to-end test, `cmd/mqtt-fixture` simulates a device. Give it a mode-0600 JSON file via `MQTT_FIXTURES_FILE` containing an array of `{ "tenant_id", "asset_id", "secret_hex" }` records, plus `MQTT_BROKER_URL=tcp://127.0.0.1:51883`. It validates the signed configure command and returns a signed `configured` acknowledgement. This executable is a test fixture, not production firmware.

## Placement routing

`SHARD_REGISTRY_FILE` routes validated saga commands and correlated device ACKs by current tenant placement. Pending configuration/result ID selectors fan out across all four explicit primaries, then customer reads/claims/marks resolve current placement again. MQTT and Kafka publication retain a durable ownership lock through external acknowledgement in registry mode and preserve existing command/result IDs for replay. Quiescing items stay pending and are skipped in polling batches. See [Go sharding contract](../../packages/go-common/SHARDING.md).
