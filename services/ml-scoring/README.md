# ml-scoring

Status: **local synthetic-only shadow vertical slice; not production-ready**. It consumes the canonical telemetry topic only after explicit opt-in, validates the v1 envelope, accepts one configured synthetic tenant, checks an immutable model bundle and golden vector, maintains six-hour-minimum per-bin windows, and writes predictions to a shadow-only table. In the same tenant-scoped transaction it creates a row in the separate `ml_shadow_outbox`; a bounded lease-based relay publishes `ml.prediction.shadowed` events to `greenguard.ml.prediction.shadow.v1`. This is not the product `outbox_events` table and it never writes `ml_predictions`, alerts, or risk decisions. The only current model is a synthetic hotspot-transition classifier, not the planned grain forecast.

## Safety and local operation

The process supports two guarded synthetic-only profiles: `local-synthetic` and `cluster-synthetic`; both require `ML_SHADOW_ENABLED=true`, `ML_SYNTHETIC_TENANT_ID`, and a model marked synthetic and production-ineligible. The cluster profile restricts PostgreSQL/Kafka endpoints to dedicated `ml-synthetic` service DNS names and requires verified TLS plus Kafka SCRAM credentials. The opt-in Helm/Argo package is disabled by default and has not been installed in a live cluster. Kafka commits are synchronous and happen only after the PostgreSQL transaction completes; replay is protected by `consumer_inbox`. Prediction and shadow-outbox rows are inserted atomically. The relay claims bounded batches (one row by default) under leases validated to outlast their delivery and database-mark time bounds, publishes with stable event IDs and Kafka producer idempotence, and marks each row published only after broker acknowledgement. Shutdown stops between records and releases all unprocessed leases; its join bound is 50 seconds (10-second Kafka delivery + two conservatively bounded 15-second database operations + 5-second final flush + margin). Kafka network waits are capped at 5 seconds for sockets and 10 seconds for requests; OTLP exporters and processors use 2-second timeouts. The opt-in Helm/Argo chart allows 90 seconds for relay join, consumer close, health-server shutdown, and bounded telemetry flushes; this is statically checked and has not been installed in a live cluster. Delivery errors release the failed and remaining rows before being reported. Three consecutive publish failures mark the relay degraded and make `/readyz` fail until the relay recovers. A crash between acknowledgement and the published mark can duplicate an event, so downstream consumers must deduplicate by event ID. While a tenant is active, inbox rows older than 30 days are pruned in batches of at most 1,000. Published shadow outbox rows older than 30 days and their matching prediction records are pruned together in the same tenant-scoped RLS transaction; unpublished outbox rows and their predictions are retained. A full cleanup batch schedules a follow-up in one minute; otherwise the next check is hourly. Configure Kafka topic retention and the supported operator replay window to be shorter than 30 days. This cleanup is a bounded local-synthetic policy and is not a production retention/restore policy. The runtime defaults to TLS (`KAFKA_SECURITY_PROTOCOL=SSL`); plaintext requires a separate explicit local opt-in. `/livez` is process liveness and `/readyz` checks readiness, PostgreSQL, and relay health. The health listener binds to `127.0.0.1` by default; exposing it remotely needs an explicit override. OTLP traces, metrics, and logs are exported only when `OTEL_EXPORTER_OTLP_ENDPOINT` is configured.

The consumer emits `ml_scoring.process_event` spans with topic, partition, offset, model name/version, mode, and result attributes. Python logs are bridged to OpenTelemetry when OTLP is configured, preserving severity and active trace context while exporting only bounded code/logger metadata; tenant IDs and arbitrary log extras are excluded. The OTel instruments include `ml_scoring_events_total`, the `ml_scoring_event_processing` and `ml_scoring_model_inference` histograms (unit `ms`), `ml_scoring_shadow_predictions_total`, `ml_scoring_shadow_probability`, `ml_scoring_input_temperature` (unit `Cel`), `ml_scoring_input_relative_humidity` (unit `%`), and `ml_scoring_input_missing_measurements_total`. The same Collector translates those to the `greenguard_otel_` Prometheus namespace with unit suffixes, for example `greenguard_otel_ml_scoring_event_processing_milliseconds` and `greenguard_otel_ml_scoring_input_temperature_celsius`. The immutable I4 synthetic bundle also carries train-split histograms for temperature and humidity. The scorer compares accepted synthetic inputs to those histograms with a bounded rolling PSI window and exports the latest PSI as the `ml_scoring_input_feature_psi` observable gauge; a value over 0.25 logs a warning only. PSI state is checkpointed as bounded histogram-bin ordinals in the forced-RLS `ml_drift_status` row and restored at startup; invalid state fails startup closed. A checkpoint write failure is logged and counted, so this remains observational local-synthetic instrumentation rather than a production-grade exactly-once drift pipeline. PSI does not trigger rollout or rollback decisions. Model metric dimensions are limited to feature, loaded model name/version, and `mode=shadow`; tenant identifiers are intentionally excluded from telemetry labels.

Apply the schema separately using the local-only migration runner, with a privileged migration URL: `ML_ENVIRONMENT=local-synthetic ML_MIGRATION_DATABASE_URL=postgresql://...@localhost:5432/greenguard_ml python services/ml-scoring/migrate.py`. The runner rejects non-local hosts and any database name other than `greenguard_ml`. Runtime credentials must use a non-owner, `NOBYPASSRLS` role; tenant tables use forced RLS and every operation sets `app.tenant_id` transaction-locally. `quarantine_samples` contains digests and reason codes only. This prototype processes one Kafka event at a time and stores bounded sequence state as JSONB and uses a fixed-size connection pool (maximum four connections by default); it is not a high-throughput design.

Install pinned dependencies and run the local tests:

```sh
python3 -m venv .local/ml-scoring-venv
.local/ml-scoring-venv/bin/pip install -r services/ml-scoring/requirements.txt
PYTHONPATH=services/ml-scoring:.:packages/ml-features/src:packages/grain-physics/src:services/risk-engine:services/grain-advisor \
  .local/ml-scoring-venv/bin/python -m unittest discover -s services/ml-scoring/tests -p 'test_*.py' -v
```

A disposable synthetic deployment also requires the shadow migration, a TLS Kafka cluster, a synthetic-only immutable bundle generated by `tools/intelligence/publish_i4_model_bundle.py`, and explicit environment configuration. Do not point this prototype at real tenant topics or production databases. Corrupt persisted sequence state and scorer/model contract failures fail fast and leave the Kafka offset uncommitted; they require operator repair instead of being mislabeled as bad tenant input.

## Still open for I5

This slice does not implement inventory/lot/risk invalidation feeds, complete as-of joins, offset-range checkpointing, contiguous batch commit, scored-through watermark events, automated/scheduled retraining execution, production rollout/rollback actuation, champion predictions, product transactional-outbox publication, a production Risk Engine consumer/apply path, live Helm/Argo deployment, DLQ operations, or production acceptance. A separate synthetic-only Kafka event is parsed by the Risk Engine shadow validator and rendered by a non-actionable Grain Advisor preview in local acceptance; that does not modify product risk state. One synthetic retraining package was generated and accepted by a fresh local controller as `verified_offline`; the run selected no candidate and remained in shadow (see `evidence/intelligence/i5-offline-retraining-acceptance.json`). Local synthetic release-controller rehearsals test immutable candidate identity, stale/nonfinite guardrails, rollback decisions and promotion blocking, but never change serving mode or external state. The scorer stores the latest tenant/model/feature PSI aggregate and bounded bin-ordinal window in forced-RLS PostgreSQL; restart restore has unit-level equivalence tests and disposable PostgreSQL integration coverage, but live DB integration has not been rerun after this change. The chart enforces a single scorer replica because distributed partition ownership/state coordination is not implemented. Drift snapshots are observational only and do not directly trigger production rollout or rollback. There is no registered production model; canary selection remains guarded by real promotion evidence. These are separate acceptance gates, not capabilities implied by configuration or architecture docs.

## Shared observability

For optional local telemetry, start the existing stack with `docker compose -f infra/observability/compose.yaml up -d`, then run the integration command with `ML_IT_OTEL_ENDPOINT=http://127.0.0.1:14317`. The harness passes only this explicit loopback OTLP endpoint to the scorer; cloud credentials and arbitrary remote exporters remain excluded. Metrics, traces, and logs appear through the existing Collector → Prometheus/Grafana/Tempo/Loki pipeline. The Grafana dashboard is `GreenGuard ML Scoring Health`; alerts and response steps are in `infra/observability/rules/ml-scoring.yaml` and `docs/runbooks/ml-scoring-observability.md`.

## Real local Kafka/PostgreSQL acceptance

`make ml-scoring-integration-test` runs an isolated one-broker/one-database Compose environment, applies the shadow migration, provisions a least-privilege non-owner `NOBYPASSRLS` runtime role, starts the real scorer, publishes 384 deterministic synthetic events, verifies an audited prediction and cross-tenant RLS denial, checks that production prediction/outbox writes are denied and offset uniqueness collisions fail closed, consumes and validates the shadow-only Kafka output event, then republishes the exact records followed by a new sentinel to prove replay idempotency and processing order. The harness selects available ephemeral loopback ports, uses disposable named container volumes, and runs `docker compose down --volumes` in its cleanup path. Its credentials and plaintext Kafka opt-in are for this disposable local test only.

`make -C services/ml-scoring failure-acceptance-test` is the isolated three-broker crash/failover acceptance. It stops the current leader while producing with RF=3/minISR=2, observes leader/ISR movement and recovery, crashes the actual scorer after a database transaction but before input offset commit, and crashes after Kafka output acknowledgement but before the outbox published mark. It verifies replays, idempotent database effects, tenant isolation, and routes newly received shadow event bytes through the strict Risk Engine parser and non-actionable Grain Advisor preview (historical replay verifies durability without counting a second preview). The passing report is written to `evidence/intelligence/i5-multibroker-shadow-acceptance.json`. The harness removes its own Compose project, volumes and network; it uses only deterministic synthetic fixtures and no external credentials.

The local three-broker acceptance proves one leader failover. It does not prove multiple scorer replicas, crash-at-every-transaction-boundary recovery, external OTLP ingestion, production tenancy, real sensor parity, or production risk/read-model integration.
